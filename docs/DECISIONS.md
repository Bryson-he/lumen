# Decisions log

Record any change from `docs/PLAN.md` here: date, what changed, why.

| Date | Decision | Why |
| --- | --- | --- |
| 2026-11-13 | Visual direction D (clean modern with pencil accents), light + dark | Chosen by Bryson from four explorations |
| 2026-11-13 | Settings app uses React + TypeScript (not Svelte) | Settled in the plan |
| 2026-11-13 | M0: `apps/settings/src-tauri` is a member of the root Cargo workspace (crate `lumen-settings`) | One `cargo build` and one `target/` for everything; lets the settings backend share `lumen-ipc` types later |
| 2026-11-13 | M0: settings crate is a plain Windows binary (no Tauri mobile `staticlib`/`cdylib` lib target) | Lumen is Windows-only; the mobile targets only add build time |
| 2026-11-13 | M0: `packages/tokens/build.mjs` generates `dist/tokens.css` (light default, dark via `prefers-color-scheme` or `data-theme`); Rust constants not generated yet | The core has nothing to draw until M5; add the Rust output then |
| 2026-11-13 | M0: added tokens `border.subtle` (dark `#2A2C31`) and `widget.glass.textMuted` (dark `#B9B8B2`) | Both colours are used in the approved designs (sidebar edge, status-strip line, muted text on glass widgets) but were missing from the token table |
| 2026-11-13 | M0: split out `danger.border` and `widget.glass.border`; their light values (`#C0392B`, `rgba(30,31,34,0.10)`) and light `widget.glass.textMuted` (`#5F5E58`) are first guesses | The plan gives these for dark only and no light mock-up uses them; review when the light Widgets screen is built (M6) |
| 2026-11-13 | M0: current toolchain is newer than the plan assumed — Rust 1.97 (edition 2024), Node 24, pnpm 12, Vite 8, TypeScript 7, Tauri 2.12; React stays on 18 as planned | Latest stable at install time; all build cleanly together |
| 2026-11-13 | M0: app icon is a placeholder (pencil-blue "L" on dark) | Tauri needs an `.ico` to build on Windows; no logo has been designed yet |
| 2026-11-13 | M1: role mapping onto Material 3 — `primary`/`secondary`/`tertiary`/`surface`/`onSurface`/`outline` are the Material roles of the same name; `neutral` is Material `surfaceContainerHigh` | The plan names the eight roles but not their Material sources; `neutral` in the example theme is a raised surface one step above `surface` |
| 2026-11-13 | M1: `accent` is not a Material role. It is the wallpaper's second colour furthest in hue from the seed (at least 45° away), else the seed's complement; tone 80 on dark, 40 on light. Monochrome uses white/black | The designs show accent as a contrasting pop colour (the sun against the blue harbour), which no Material role gives |
| 2026-11-13 | M1: variants map to Material TonalSpot, Vibrant, Expressive, Monochrome; `contrast` is stored as -1/0/1 (the slider's Reduced/Standard/High) and passed to Material as -1.0/0.0/1.0 | Matches the three-step slider and the `"contrast": 0` in the plan's example |
| 2026-11-13 | M1: generated dark surfaces are darker than the design mock-ups (about `#0E1513` vs `#1C1D21`) | Material's dark surface is tone 6; kept as generated so contrast guarantees hold. Revisit in M4 if it looks too dark behind widgets |
| 2026-11-13 | M1: the image is sampled on a ~128-point grid straight from the decoded pixels instead of being resized with `image` first | Same result for palette purposes, and skips a full-image resize; decode is the only real cost |
| 2026-11-13 | M1: grey or near-monochrome wallpapers seed from their own faint tint, not Material's stock blue fallback | A grey wallpaper producing a blue theme would look unrelated to the image |
| 2026-11-13 | M1: no CLI argument crate (clap); arguments are parsed by hand | Two commands and five flags; keeps `lumen-theme` (a dependency of the always-on core) small |
| 2026-11-13 | M1: extraction (`extract` -> `SourceColors`) and generation (`Theme::generate`) are separate public steps | Lets the core cache each wallpaper's colours so switching variant or mode never re-reads the image |
| 2026-11-13 | M2: fullscreen watching is event-driven with out-of-context WinEvent hooks (`EVENT_SYSTEM_FOREGROUND` everywhere, `EVENT_OBJECT_LOCATIONCHANGE` only on the foreground window's thread) | No polling, so it costs nothing at idle; out-of-context hooks run in Lumen's process, so nothing is injected into games. Scoping the move/resize hook stops mouse movement waking Lumen |
| 2026-11-13 | M2: "fullscreen" = Windows reports D3D exclusive fullscreen, or the foreground window covers its whole monitor and has no title bar (or Windows reports "busy"). Desktop, taskbar and Task View are excluded by window class | The plan's two signals, plus the title-bar test so a maximised window with an auto-hidden taskbar is not treated as a game |
| 2026-11-13 | M2: fullscreen detection never opens the other process (no exe name); it reports window title and class only | Keeps the anti-cheat rule strict; the title is enough for logs and the status strip |
| 2026-11-13 | M2: setting the accent also writes `AutoColorization = 0`; `accent::snapshot()` / `restore()` put back every value touched, deleting ones that did not exist | Otherwise Windows replaces Lumen's accent on the next wallpaper change. Snapshot/restore is what M3's preview/revert will use |
| 2026-11-13 | M2: the accent's light/dark shades (`AccentPalette`) are simple blends toward white and black, not Windows' own algorithm | Windows' shade algorithm is not public; blends look close. Revisit if Start or Settings highlights look off |
| 2026-11-13 | M2: monitors are numbered left to right, then top to bottom; the stable identifier stored in files will be Windows' monitor device path | Numbers are for people, device paths survive reboots and re-plugging |
| 2026-11-13 | M2: hotkeys (`RegisterHotKey`) are not in `lumen-win` yet | Not part of M2's done-check; first needed for edit mode in M6 |
| 2026-11-13 | M2: `lumen-win` reuses `lumen_theme::Color` and `Mode` | One colour and mode type across crates instead of converting between copies |
| 2026-11-13 | M3: `lumen-core` has two threads — main (Win32 message loop: tray icon + fullscreen watcher) and service (single-threaded tokio: state, pipe server, preview timer). The tray is plain Win32, no tray crate | Smallest footprint that still keeps Windows message handling and async I/O apart; measured about 18 MB working set at idle |
| 2026-11-13 | M3: IPC framing is one JSON-RPC 2.0 object per line on `\.\pipe\lumen-core`; events are JSON-RPC notifications pushed to every connected client. Error codes: standard JSON-RPC plus 1 no preview, 2 not found, 3 Windows refused | The plan fixes pipe + JSON-RPC but not framing; newline-delimited is the simplest to read from Rust, JS and by hand |
| 2026-11-13 | M3: `previewTheme` takes either a complete `theme` or generation inputs (`source`, `variant`, `mode`, `contrast`, `style`, `setWindowsAccent`, `name`); anything left out comes from the current theme | Generation lives in the core (it has the cached wallpaper colours), and the settings app can change one control at a time |
| 2026-11-13 | M3: applying a theme means — its source wallpaper on every monitor, Windows light/dark set to the theme's mode, and, if `setWindowsAccent`, the Windows accent set to the `primary` role | The plan lists what a theme can drive but not which role feeds the Windows accent; `primary` is the theme's main colour. Per-monitor wallpapers come from presets |
| 2026-11-13 | M3: the desktop is snapshotted before the first preview; further previews reuse that snapshot and restart the 15 s timer. Revert, auto-revert and quitting all restore it. Starting the core never re-applies the kept theme | Revert must always return to the look from before the user started trying things; start-up must not change the desktop |
| 2026-11-13 | M3 known gap: the preview snapshot is in memory only, so if `lumen-core` is killed or crashes mid-preview the desktop stays in the previewed state | Clean exits (tray Quit, WM_CLOSE, Windows sign-out) do revert. Writing the snapshot to disk and restoring it on next start is a small follow-up if this bites |
| 2026-11-13 | M3: telling running apps about a light/dark or accent change now happens on a background thread (`lumen-win`), merged if several arrive together | Found in the live check: the Windows broadcast blocks 1.5–4.5 s while every open window re-themes, which made previews slow and the 15 s revert late |
| 2026-11-13 | M3: `AccentPalette` entries are written as red, green, blue, 0 and the eighth entry is kept from the existing palette | Matches what Windows itself stores (seen on this PC); M2 wrote 0xFF in the fourth byte |
| 2026-11-13 | M3: `applyPreset` reads `presets/<id>.json` (name, theme file, wallpaper per monitor id or `"all"`, opaque widgets/bar) and commits straight away | Enough for the IPC method and Quick switch; saving, exporting and the `.lumen` zip are M7 |
| 2026-11-13 | M3: imported wallpapers are copied to `wallpapers/<id>.<ext>` with an index (`wallpapers/index.json`) holding each one's extracted colours and a content hash; re-importing the same image returns the existing entry | "Each wallpaper stores its extracted palette, so switching is instant"; the hash avoids duplicates |
| 2026-11-13 | M3: only one `lumen-core` can run (it owns the pipe); `LUMEN_DATA_DIR` and `LUMEN_PIPE` override the data folder and pipe name | Single instance without extra machinery; the overrides are for tests and clean-profile checks (M7) |
| 2026-11-13 | M3: idle CPU is not exactly zero (about 0.03% of the whole CPU) | The fullscreen watcher is woken by move/resize events from whatever app is in front. Well inside the 0.5% budget; revisit in M8 with the governor |
| 2026-11-13 | M4: the core gained `getStatus`, `listMonitors`, `setWallpaper`, `updateWallpaper`; `previewTheme` takes `wallpaperMonitor`; wallpapers get a 640 px JPEG thumbnail, a favourite flag and tags | The three screens need them (status strip, "Show on", favourites and tag filters, tiles that do not load 4K images) and the plan's method list did not cover them |
| 2026-11-13 | M4: "Set as wallpaper only" applies at once, with no Keep/Revert bar | The preview machinery is about themes; a wallpaper-only change has no theme to keep. It departs from "every change gets Keep/Revert" for this one button; revisit if it feels inconsistent |
| 2026-11-13 | M4: Home's "Active preset" card shows the active theme, and Quick switch offers the three newest wallpapers as one-click looks; Shuffle previews a random other wallpaper | Presets do not exist until M7. Quick switch moves to presets then |
| 2026-11-13 | M4: the Keep/Revert bar lives in the shell and shows on every screen while a preview is up, with the seconds left | Previews can start from Home, Wallpapers and the command palette, not only the Theme screen |
| 2026-11-13 | M4: Mode "Auto" picks light or dark once from the wallpaper's (or colour's) brightness; it is not stored in the theme | A theme file holds light or dark only. Following Windows or a sunset schedule is a core feature for a later milestone |
| 2026-11-13 | M4: fine-tuning a swatch sends the whole theme; changing variant, contrast or source afterwards regenerates all eight roles and drops the tweak. "Manual" marks the theme as hand-made and disables the generator controls | Simple and predictable; keeping per-role overrides across regeneration would need an overrides field in the theme format |
| 2026-11-13 | M4: the app's pencil accent follows the active theme's `primary` only when the theme's mode matches the app's (the app follows Windows) | A primary made for dark surfaces is too pale on a light app, and vice versa; otherwise the default pencil blue is used |
| 2026-11-13 | M4: fonts come from the `@fontsource` npm packages and are bundled by Vite (no network at run time) | "Bundle the font files locally"; packages keep the licences and updates tidy |
| 2026-11-13 | M4: the settings backend owns one pipe connection, starts `lumen-core.exe` from its own folder if the pipe is absent, and reconnects if the core stops. `cargo tauri dev` builds the core first | The app must work when opened on its own, and from the tray |
| 2026-11-13 | M4: the page may read images only from Lumen's data folder, allowed at run time once the core reports where that is | Thumbnails need file access; a fixed `%APPDATA%` scope would break with `LUMEN_DATA_DIR` and a wide scope is unnecessary |
| 2026-11-13 | M4: Presets, Widgets, Bar, Plugins, Gallery and Settings are placeholder pages in the shell style; the command palette covers navigation, Keep/Revert, import and "make theme from …" | Those screens belong to later milestones |
| 2026-11-13 | M4: new tokens — radii `kbd`, `segment`, `barButton`, `swatch`; colours `button.outline.bg`, `swatch.ring`, `scrim` | Values used in the design files (or needed for the palette backdrop) that had no token |
| 2026-11-13 | M4: setting a wallpaper on all monitors now checks each monitor afterwards and sets any that was missed | Seen once on the two-monitor PC: the all-monitors call changed one monitor and left the other |
